## Choose the operation by what is missing

Read `id_constraints` before choosing an operation:

- An ID in `node_ids` already identifies a BPMN node. Never create it again.
- An ID in `flow_ids` already identifies a sequence flow.
- An ID in `gateway_ids` identifies an existing gateway.
- A node with no incoming or outgoing flow is missing a connection, not a node.

Use these operation meanings:

- `add_flow`: connect two nodes in one existing process. Set `process_id` to
  that process, use a new sequence-flow `id`, and use existing `source_ref` and
  `target_ref` node IDs (or a node created earlier in this plan). Its fields are
  `op`, `process_id`, `id`, `source_ref`, `target_ref`, `name`, and
  `condition_expression`; it does not use `node_type`.
- `remove_flow`: delete an existing sequence flow.
- `change_gateway_type`: change one existing gateway to another gateway type.
- `remove_node`: delete an existing leftover node; set `cascade=true` when its
  incident flows must also be removed.
- `rename_node` / `rename_flow`: change only a displayed name.
- `set_condition`: change only an existing flow's condition.
- `change_node_type`: correct the type of an existing node. Do not use it to
  repair connectivity, and use `change_gateway_type` for gateway-to-gateway
  changes.
- `add_node`: introduce a genuinely absent BPMN activity, event, or gateway.
  Never use `add_node` to represent a missing sequence flow. Every new node must
  be connected by at least one `add_flow` in the same plan.

Identifiers such as `sf_*`, `flow_*`, or names describing “A to B” normally
denote sequence flows. Create them with `add_flow`, not `add_node`.

## Interpret findings

Each issue may contain `rule_id`, `severity`, `tier`, `source`, `message`,
`affected_elements`, and formal evidence.

For connectivity findings:

- “start event has no outgoing flow” → connect that existing start event with
  `add_flow`, or remove the existing event if it is clearly leftover.
- “end event has no incoming flow” → connect an existing upstream node to that
  existing end event with `add_flow`, or remove the redundant end event.
- “cannot reach an end event” → repair the missing or incorrect downstream
  connection. Do not create a task named after the desired flow.

Several findings can be symptoms of one omission. For example, an existing task
that cannot reach an end and an existing end with no incoming flow may require
one `add_flow` from the task to the end, not two edits.

Tier-2 `dead_elements` and `uncovered_elements` identify existing BPMN elements
involved in the formal failure; they are not requests to create replacements.
For a split/join mismatch, inspect the existing branch semantics and prefer a
local gateway-type or flow correction.

Treat `other_open_issues` only as background. Do not fix them, but avoid making
them worse.

For a semantic finding, preserve behavior that agrees with
`reference_description`. Make only the change that removes the contradiction.

## Plan checks

Before returning the plan, verify:

1. Every ID in `affected_elements` was looked up in `id_constraints`.
2. Existing affected nodes are referenced, not recreated.
3. Every `add_flow.process_id` is an existing process, and both its
   `source_ref` and `target_ref` nodes belong to that process.
4. Every `add_node` is necessary and connected within this plan.
5. Shared root causes use one edit rather than duplicate edits.
6. Every assigned issue is addressed, with no unrelated changes.

On a correction attempt, return a complete replacement plan that incorporates
`repair_feedback`; do not return a patch to the rejected plan. Reconsider the
operation type rather than inventing alternative IDs for the same rejected
operation. Return one solution only—never enumerate candidate names or plans.

Use the provider response schema. Its required `description` briefly explains
the plan for a human reviewer; put the ordered operation list in `result.ops`.
Do not use markdown.
