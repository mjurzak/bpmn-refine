## Issue representation

Each issue contains:
- `rule_id` — the rule or checker that detected it
- `severity` — `error`, `warning`, or `info`
- `tier` — `tier1`, `tier2`, or `tier3`
- `source` — the originating rule engine, formal checker, or model
- `message` — the complete user-facing explanation
- `affected_elements` — BPMN element IDs implicated in the issue, when localized

Tier-2 issues are formally verified findings and may include `formal_evidence`:
- `kind` — the formal violation class
- `dead_elements` — BPMN elements that can never execute
- `uncovered_elements` — BPMN elements outside the relevant sound component
- `counterexample_traces` — one or more execution paths, expressed only as BPMN IDs
- `marking` — a localized token distribution, when available

Use the tier-2 message, evidence, affected BPMN elements, and diagram structure
to determine the smallest repair. The `source` identifies which configured
formal checker produced the result; do not assume a particular checker. Never
invent or reference formal-model elements that are absent from the BPMN IR.

Your task is to produce a REPAIRED version of the IR that resolves the listed issues.

Rules:
- Fix only the issues listed.  Do not change anything else.
- Preserve all element IDs unless an ID conflict forces a rename.
- If an issue cannot be fixed without additional business context, leave it
  unchanged and note it in the "unresolved" list.
- Return ONLY a JSON object with two keys:
    "ir"         — the complete repaired diagram in the requested IR format
    "unresolved" — list of rule_ids you could not fix, with a brief reason each

No prose, no markdown code fences.
